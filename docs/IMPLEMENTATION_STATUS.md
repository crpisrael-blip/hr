## תמצית

הליבה העסקית — CRM, מועמדים, מועמדויות, משימות, וכל מודול הכספים
(מדרגות שוליות, לוח תשלומים, קיזוזים) — **ממומשת ונבדקת**. מנוע הטפסים,
השדות המותאמים, כרטיס המשרה וניהול העובדים (גרסאות 0.9–0.12) ממומשים.

הפער המרכזי הוא **ארכיטקטורלי**: האפיון בנוי סביב שכבת API (Hono) שהיא נקודת
אכיפת ההרשאות היחידה, ו-RLS כרשת ביטחון שנייה. בפועל אין שכבת API — ממשק
הצוות פונה ל-PostgREST ישירות, וה-RLS היא policy אחת גורפת (`staff_all`).
ממנו נגזרים רוב הפערים בטבלה למטה: מטריצת ההרשאות, היקפי "שלי", הסתרת שדות
רגישים ואכיפת מעברי שלב — כולם הוגדרו לחיות בשכבה שלא נבנתה.

## ההחלטה שצריך לקבל

פריטים 1, 2, 3, 5 ו-16 הם כולם ביטוי אחד של אותה החלטה פתוחה. שתי דרכים:

**א. לבנות את שכבת ה-API** כפי שהאפיון מתאר (Edge Function עם Hono), להעביר
אליה את כל הקריאות מממשק הצוות, ולהשאיר את RLS כרשת ביטחון. נאמן לאפיון,
עבודה משמעותית, ומחייב לגעת בכל מסך בממשק הצוות.

**ב. להכריז על RLS כמנגנון האכיפה הראשי**, לכתוב policies אמיתיות שנגזרות
מ-`permission_defaults` / `permission_profiles` / ה-overrides במקום `staff_all`,
ולעדכן את האפיון בהתאם. פחות קוד, אכיפה קרובה יותר לנתונים, אך כל כלל הרשאה
נכתב ב-SQL.

**כל עוד ההחלטה לא התקבלה, קריטריוני הקבלה של האפיון בסעיפים אלה אינם מתקיימים.**
ה-`staff_all` הנוכחית משמעותה שכל משתמש מחובר מהצוות רואה וכותב הכל.
